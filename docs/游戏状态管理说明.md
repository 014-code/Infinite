# 游戏状态管理说明

`src/game/state/` 提供的是“应用流程状态”，用于组织主菜单、游戏中、暂停和结算等阶段；它不是 `Scene` 中的 `GameObject`，也不替代保存玩家数据的游戏会话对象。

## 为什么使用状态栈

游戏通常不是只有一个永远运行的场景：

```text
MainMenuState
    ↓ Push
GameplayState
    ↓ Push
PauseState
    ↓ Pop
GameplayState
    ↓ Replace
ResultState
```

状态栈适合表达“暂停菜单覆盖在游戏上面”的关系：暂停状态位于栈顶，接收输入并显示菜单；下面的游戏状态仍然保留，但可以通过 `StateFramePolicy` 停止场景更新和物理模拟。

## 一个最小状态

```cpp
#include "game/state/ApplicationState.h"

class GameplayState final : public ApplicationState
{
public:
    void onEnter(ApplicationStateContext &context) override
    {
        // 这里只放进入游戏时的一次性准备，例如创建场景对象或播放音乐。
        (void)context;
    }

    void onEvents(ApplicationStateContext &context) override
    {
        if (context.application().input().wasKeyPressed(Key::Escape))
        {
            // 请求会排队，在下一帧事件阶段开始前提交。
            context.push<PauseState>();
        }
    }

    void update(ApplicationStateContext &, float deltaTime) override
    {
        // 普通帧逻辑；固定物理逻辑应放在fixedUpdate。
        (void)deltaTime;
    }
};
```

状态回调不能直接修改状态栈容器。`push`、`pop`、`replace`、`clear` 和 `quit` 都只是提交请求，框架会在安全边界按顺序执行。这样即使 `onEvents` 请求了 `replace`，当前回调返回前当前对象仍然有效。

## 启动状态栈

```cpp
Application application(config);
ApplicationStateStack states;
states.push<MainMenuState>();
application.run(states);
```

初始状态必须在 `run` 前 Push 一次。启动后再次调用 `push` 会进入排队流程；退出时状态栈会按从栈顶到栈底的顺序调用 `onExit`。

## 生命周期顺序

单个状态可能收到这些回调：

```text
onEnter
    onEvents
    update
    fixedUpdate（可能一帧多次）
    afterPhysics
    afterRender
onPause / onResume
onExit
```

- `onEnter`：状态成为栈顶时调用一次。
- `onPause`：另一个状态 Push 到它上面时调用。
- `onResume`：上层状态 Pop 后重新成为栈顶时调用。
- `onExit`：状态被 Pop、Replace、Clear 或应用退出时调用。
- `onEvents`：每帧事件阶段调用，即使状态策略暂停了场景和物理也会收到。
- `update`：可变帧更新；用于菜单动画和非物理逻辑。
- `fixedUpdate`：固定物理子步；一帧可能调用多次，不能依赖“每帧只调用一次”。
- `afterPhysics`：物理同步后、场景更新前调用。
- `afterRender`：场景绘制后、交换窗口前调用。

状态对象由 `ApplicationStateStack` 独占。不要让状态把自己的 `this` 保存到异步任务中，也不要在 `onExit` 返回后继续访问它。

## 暂停策略

默认策略全部开启：

```cpp
StateFramePolicy framePolicy() const noexcept override
{
    return {};
}
```

暂停状态通常这样写：

```cpp
StateFramePolicy framePolicy() const noexcept override
{
    StateFramePolicy policy;
    policy.updateScene = false;
    policy.simulatePhysics = false;
    policy.renderScene = true;
    policy.updateAudio = true;
    return policy;
}
```

这里的策略只控制 `Application` 共享服务。状态仍会收到自己的 `onEvents`、`update` 和 `afterRender`，因此 UI 可以继续响应输入并绘制暂停菜单。暂停时物理累加器会被清空，恢复后不会把暂停期间的时间一次性补模拟。

音频是否真正暂停由状态和 `AudioSystem` 的使用方式决定；`updateAudio = false` 只是不推进音频系统的每帧更新，不会自动替所有 Voice 改变播放状态。

## 切换操作的语义

| 操作 | 行为 |
| --- | --- |
| `push(State)` | 暂停当前栈顶，进入新状态；适合暂停菜单和临时覆盖层 |
| `pop()` | 退出当前状态，恢复下面的状态；栈为空时请求关闭应用 |
| `replace(State)` | 退出当前状态并进入新状态；适合从菜单进入游戏、游戏进入结算 |
| `clear()` | 退出所有状态并请求关闭应用 |
| `quit()` | 请求关闭应用，但保留当前状态直到统一退出清理 |

单帧状态切换最多提交 1024 条命令。这个限制用于发现状态逻辑中的无限切换，而不是作为正常流程控制手段。

## 当前边界

状态栈目前只负责生命周期、切换和主循环策略，不负责：

- UI 控件和菜单布局；
- SceneManager 或异步关卡加载；
- 保存游戏进度；
- 自动播放背景音乐；
- 网络连接和联机状态。

这些功能会在上层模块逐步接入，状态类仍然只负责组织它们，不把具体游戏规则写回引擎核心。
